# 售后

## 用户目标

查询退货退款和实际收货，上传普通售后或无信息件，并确认收货或售后单。

## 能力路由

| 业务能力 | 类型 | action |
| --- | --- | --- |
| 售后上传 | 写入 | `aftersale_upload` |
| 无信息件售后上传 | 写入 | `aftersale_noinfo_upload` |
| 售后退货退款查询 | 查询 | `refund_single_query` |
| 确认收到货物 | 写入 | `webapi_aftersaleapi_confirmgoods` |
| 实际收货查询 | 查询 | `aftersale_received_query` |
| 售后单确认 | 写入 | `webapi_aftersaleapi_open_confirm` |

## 执行要点

- 优先用售后单号、原订单号或官方支持的业务标识建立对应关系，并区分仅退款、退货退款、换货和补发。
- 售后上传不会直接改变原订单状态；发货前拦截商品可能还需要订单退款状态或整单取消，结合[订单](orders.md)判断。
- 其他平台已经下载到ERP的售后单不能通过普通上传接口修改；作废状态售后单再次上传也可能无效。
- 售后退货退款查询不覆盖部分淘系和拼多多数据。查不到时说明平台能力和近3个月等限制，不判断为“没有售后”。
- “退回了吗”要区分买家提交、买家发货、卖家确认收到、实际退仓和最终确认；根据问题选择售后查询或实际收货查询。
- 实际收货记录可能因取消收货产生负数，汇总实际退仓数量时不能简单过滤负数。
- 无信息件只用于确实无法匹配原始业务信息的场景，不作为普通售后的替代入口。
- 批量确认收货可能出现全部失败或部分成功，必须按实际返回报告，不能因为HTTP成功就宣称全部售后单成功。
- 返回结果时避免无必要地展示客户电话和完整地址。

## 结果呈现

- 优先展示售后单号、原订单号、售后类型、当前阶段、退款金额、货物状态和实际收货数量。
- “退款了多少”按金额汇总；“退回多少件”按实际收货明细汇总，两者不得混为同一个完成状态。
- 负数收货记录参与净收货口径，同时单独提示存在取消收货或冲销记录。
- 批量确认按成功、失败、未知三类报告；未知状态不自动重试，并提示到聚水潭后台核对。
- 空结果要说明平台范围、近3个月等查询限制，不能直接回答“没有售后”。

## 典型问题

- “SO001 的退货到仓了吗？”：串联售后状态与实际收货，回答是否已寄回、已收多少及是否完成确认。
- “本月退款金额和退回件数分别是多少？”：分别汇总金额与净收货数量，写清时间和平台覆盖范围。
