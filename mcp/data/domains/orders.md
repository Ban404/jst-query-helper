# 订单

## 用户目标

查询商家自有商城或跨境线下订单，跟进仓库、状态和发货；处理订单上传、取消、拆分、异常、备注、标签和发货。

## 执行要点

- 先确认用户提供的是线上订单号、内部订单号还是商家订单号，并按官方字段查询；不要把不同编号放入同一个字段反复试探。
- 普通订单上传仅适用于商家自有商城、跨境线下和B2B，单次最多50单；相同 `shop_id + so_id` 在发货前可能被识别为更新。
- 上传订单时核对商品成交额、优惠、运费、应付和实付金额之间的关系；除待付款状态外，按官方要求提供支付信息。
- 订单查询和上传均不等于覆盖所有电商平台。淘系、拼多多或其他受限平台数据缺失时说明奇门、方舟或敏感字段权限边界。
- “为什么没发货”先查订单状态和指定仓，再读取[出库](outbound.md)确认是否产生销售出库，必要时读取[库存](inventory.md)核对可配货库存。
- 取消、拆分、转异常和指定发货仓前先查询当前状态，确认订单尚处于官方允许变更的阶段。
- 卖家备注、线下备注和订单标签是不同字段；用户说“备注一下”时先判断要影响哪种业务信息。
- 发货要区分订单层发货与仓库出库发货。需要仓库执行和物流信息时结合[出库](outbound.md)及[基础信息](basic-info.md)。
- 部分商品退款与整单取消不是同一场景。发货前售后拦截应结合[售后](after-sales.md)和官方退款状态处理，不擅自取消整单。

## 结果呈现

- 单笔订单先给“当前处于什么阶段”的结论，再展示订单号、店铺、仓库、下单/付款时间、应付金额和物流单号。
- 将平台状态翻译成等待付款、等待发货、运输中、已完成、已关闭等业务语言；保留无法可靠翻译的原值并注明来自聚水潭。
- 列表摘要按订单数统计，金额另行合计并标明口径；不能把商品明细行数当作订单数。
- “为什么没发货”需要联合说明订单状态、指定仓、销售出库和库存证据，并指出卡在哪个环节。
- 取消、拆分、备注和发货结果要用受影响订单号逐项说明；部分成功时分开列出成功与失败订单。

## 典型问题

- “SO001 为什么还没发货？”：依次核对订单、出库和库存，回答阻塞环节及建议动作。
- “昨天已付款但未发货的订单有多少？”：按明确时间和状态查询，给出订单数、金额口径和代表性订单，说明是否还有后续页。
- “给这三单加急并备注今天发”：区分标签与卖家备注，使用不同业务动作并分别报告结果。
