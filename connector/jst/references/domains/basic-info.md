# 基础信息

## 用户目标

用于识别后续业务需要的店铺、仓库、物流公司、合作伙伴或商家用户。用户只知道名称时，先查询并匹配官方 ID，不要求用户自己查 ID。

## 能力路由

| 业务能力 | 类型 | action |
| --- | --- | --- |
| 店铺查询 | 查询 | `shops_query` |
| 物流公司查询 | 查询 | `logisticscompany_query` |
| 仓库查询 | 查询 | `wms_partner_query` |
| 分销商列表查询 | 查询 | `api_drp_inneropen_partner_supplier_querymychannel` |
| 供销商列表查询 | 查询 | `api_drp_inneropen_partner_channel_querymysupplier` |
| 商家用户信息 | 查询 | `webapi_userapi_company_getcompanyusers` |

## 执行要点

- 用户说“北京仓”“旗舰店”等名称时，先查询候选项，再用名称和 ID 消除歧义；同名对象由用户选择，不自行猜测。
- 店铺查询只返回ERP中已启用的店铺。用户发现数量少于ERP页面时，提示检查店铺是否启用。
- 仓库查询只返回已生效仓库，不返回已作废仓库；后续发货、采购、盘点和调拨优先复用查询到的仓库编号。
- 物流公司需要结合仓库使用时，传入正确的分仓编号，避免把“平台支持的物流公司”误当成“当前商家、当前仓库已接入且生效的物流公司”。
- 分销商与供销商方向不同，先判断用户要查“我的分销商”还是“我的供应商”，不要混用关系。
- 商家用户信息对应ERP“用户及权限”，只展示完成任务所需内容，不主动扩散手机号等个人信息。

## 结果呈现

- 店铺、仓库和物流公司优先以“名称（编号）”展示；同名候选必须并列，不替用户选定。
- 先说明共找到多少个可用对象，再列出完成后续任务需要的候选；默认不展示创建人、内部备注等无关字段。
- 空结果要明确查询的是店铺、仓库还是物流公司，并提示检查启用状态、分仓范围或公司选择。

## 典型问题

- “聚水潭里北京仓的编号是多少？”：查询仓库，返回匹配名称、仓库编号和是否存在同名项。
- “这家公司有哪些能发货的店铺和物流？”：分别查询店铺与物流公司，按对象类型分组，不把两类编号混在一起。
